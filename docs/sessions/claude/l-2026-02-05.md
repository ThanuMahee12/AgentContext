### 2. PathSeek Project Discussion & Architecture

#### Project Goal
PathSeek is a filesystem path analysis and discovery tool for data engineers. It solves common pain points with scattered Linux commands (`find`, `stat`, `ls -l`, `glob`, `regex`, `mtime`, etc.) by combining them into a single tool.

#### Scope

**In scope** (filesystem metadata only):
- Scanning, metadata (stat), filtering, counting, grouping
- Pattern extraction (glob + regex) - existing feature
- Directory comparison (file count, missing, size differences)
- Duplicate detection (inode + hashlib)
- Validation (empty, broken symlinks, permissions)
- Search by glob and regex

**Out of scope:**
- File content parsing (CSV/JSON/Parquet internals) → data-alchemy's job
- Encryption/decryption → needs keys, domain logic
- Data quality (schema, row counts, nulls) → application-specific
- Compressed file internals → application-specific

**Rule:** If `os.stat()` + `os.scandir()` + `hashlib` can answer it → PathSeek. If you need to open and understand the file → not PathSeek.

#### Why Python Over Rust
- **Disk I/O is the bottleneck** - scanning reads from disk, both languages wait the same time
- Python works everywhere - `pip install` vs platform-specific binaries
- Rust binaries can hit glibc version mismatches across Linux environments
- `os.scandir()` is C-backed, fast enough for real-world directory trees
- Development speed matters more at this stage

#### CLI Commands First, Dashboard Later
- Functions must be scriptable and pipeable (`pathseek find /data --mtime -7 | wc -l`)
- Existing interactive dashboard (`feature/cli-questionary`) sits on top as `pathseek run`
- Build the core functions first, decide approach/UI later
- All functions return structured data: table (default), JSON (`--format json`), pipe-friendly

#### Stream-Based Architecture (Key Design Decision)

**Problem with current tree-based approach:**
```
scan → build ALL PathNode objects in memory → walk tree → filter
```
- Loads everything before processing
- 10,000 files = 10,000 objects in memory
- First result only after full scan

**New stream-based approach:**
```
os.scandir() → yield ONE entry → filter → metadata → filter → output
```
- Generator pipeline, yields one at a time
- Constant memory regardless of directory size
- First result immediate
- Ctrl+C stops cleanly

**Pipeline:**
```
┌─────────┐   ┌──────────┐   ┌────────┐   ┌────────┐
│  scan()  │──▶│ metadata │──▶│ filter │──▶│ output │
│ yield ←  │   │ yield ←  │   │ yield ←│   │        │
└─────────┘   └──────────┘   └────────┘   └────────┘
  Generator     Generator      Generator     Consumer
```

Each layer is lazy - only produces when the next layer asks.

#### Filter Design: Callback List (Not Builder Pattern)

**Rejected builder pattern** - over-engineering, violates SOLID for this use case.

**Chosen approach:** Simple `list[Callable]` passed to scan/metadata functions.

```python
# Filters are just functions
def by_extension(ext): return lambda entry: entry.name.endswith(ext)
def by_min_size(size): return lambda info: info.size >= size

# Combine with built-in all()
filters = [by_extension(".csv"), by_min_size(1024)]
scan(path, filters=filters)
```

Two lists split by **type** (not by design):
- **Scan filters** → `list[Callable[[DirEntry], bool]]` (free, no syscall)
- **Stat filters** → `list[Callable[[FileInfo], bool]]` (after `os.stat()`)

**Filter priority (cheapest first):**
```
1. Name/extension/hidden  (FREE - string check)
2. Type file/dir          (FREE - DirEntry cache)
3. Depth                  (FREE - counter)
─── stat boundary ───
4. Size                   (1 stat call)
5. Time (mtime/ctime)     (same stat call)
6. Permissions/owner      (same stat call)
─── expensive boundary ───
7. Hash (duplicate)       (reads file bytes)
8. Mime type              (reads file header)
```

**Early filtering matters:** For 50,000 files, filtering by `.csv` first (free) reduces stat calls from 50,000 to 5,000.

#### Functional + OOP Mix

| | Functional | OOP |
|---|---|---|
| **Where** | Scanner, filters, metadata, hasher, operations | Models, cache, session |
| **Why** | Stateless, composable, testable | State management, encapsulation |

**Rule:** Data flows through functions. State lives in objects.

#### Concepts Discussed

**inode vs hash checksum:**
- inode = filesystem ID (like a primary key in DB), free from `os.stat()`
- hash = content fingerprint computed by reading file bytes
- Same inode = same physical file on disk (hard link, not a duplicate)
- Different inode + same hash = true duplicate (wasting space)
- Rename doesn't change either (only changes the name pointer)
- `rsync`/`cp` creates new inode, `mv` on same filesystem preserves inode

**Duplicate detection strategy (staged, cheapest first):**
1. Group by size (instant, eliminates most)
2. Check inode (free, skip same file)
3. Partial hash first 4KB (fast, catches almost all)
4. Full hash sha256 only remaining candidates (rare)

**Encrypted vs decrypted:** Different hash - not PathSeek's scope. Comparing encrypted vs decrypted needs keys and domain logic.

**Disk I/O bottleneck:** CPU barely works during scanning - it's waiting on disk. That's why Python vs Rust doesn't matter for this use case.

#### Parallelism Decision

**Where it helps:**
- Compare two directories (scan both simultaneously)
- Duplicate hashing (hash multiple files in parallel, CPU-bound)
- Multiple path scans

**Where it doesn't help:**
- Single directory scan (same disk bottleneck)
- os.stat calls, filter callbacks, count/group (too fast)

**Decision:** Build single-threaded first. Add `ThreadPoolExecutor` later only where profiling proves it's needed. File I/O releases GIL so threads work for disk operations.

#### Submodule Split Decision
- File-watcher project mentioned as future project
- Decision: **Don't split yet.** Build everything in PathSeek first
- Splitting too early = import complexity, version coordination, deployment overhead
- Once functions are stable and a clear boundary exists, extract shared library

### 6. Additional Discussions

#### Current Regex Capability Gap
- PathSeek only **generates** regex/glob patterns from paths (paths → patterns)
- Does **NOT** support using regex to **search/filter** files (patterns → paths)
- `pathseek regex scan` outputs patterns like `\d{4}/\d{2}/.*\.csv` but can't use them to find files
- Issue #32 (Search) and #30 (Scan filters) will add `by_name_regex(pattern)` callback

#### AI/ML/NLP for PathSeek? - No
- Discussed whether PathSeek should use AI/ML/NLP for path analysis
- **Decision: No.** PathSeek works with deterministic filesystem data - zero ambiguity
- A file is 1024 bytes or it isn't. `*.csv` matches or it doesn't. No ML needed
- AI adds: heavy deps (torch), slower (inference vs string), less accurate (ML can be wrong, regex can't), breaks "works everywhere" (GPU)
- PathSeek is a utility tool like `find`/`stat`/`tree` - rule-based, fast, deterministic
