### 2. PathSeek Project Planning & Architecture

**Scope defined:**
- Filesystem path analysis tool for data engineers
- In scope: scan, metadata (stat), filter, count, group by, search, compare, duplicate detection, validate, pattern extraction
- Out of scope: file content parsing, encryption/decryption, data quality
- Rule: If `os.stat()` + `os.scandir()` + `hashlib` can answer it → PathSeek

**Key decisions:**
- **Python over Rust** - disk I/O is the bottleneck, not CPU. Python works everywhere
- **CLI commands first, dashboard later** - functions must be scriptable and pipeable
- **Stream-based architecture** - generators, not tree-in-memory. Constant memory, immediate first result
- **Callback filters** - simple `list[Callable]`, no builder pattern. Two lists split by type (DirEntry vs FileInfo)
- **Functional + OOP** - functions for processing, classes for state
- **Filter priority** - cheapest first: name/ext (free) → type (free) → depth (free) → size (stat) → time (stat) → hash (file read)
- **No submodule split yet** - build everything in PathSeek first, split later if needed

**Concepts discussed:**
- inode vs hash checksum (inode = filesystem ID, hash = content fingerprint)
- Duplicate detection: different inode + same hash = true duplicate
- Encrypted vs decrypted files: different hash, not PathSeek's scope to compare
- Disk I/O bottleneck: why Python vs Rust doesn't matter for scanning
- Early filtering: reject files before expensive stat calls
