## Root Cause Analysis (CORRECTED)

### Error Source: `upsert_metadata` (NOT fallback path)

The disk I/O errors come from `upsert_metadata` (db.py:558-566):

```python
# db.py lines 558-566 - runs for EVERY file processed
existing_record_stmt = select(FileMetadata).where(
    and_(
        FileMetadata.input_filepath == input_fp,
        FileMetadata.stratum == stratum,
        FileMetadata.requires_reprocessing_time.is_not(None),  # matches error SQL
        FileMetadata.reprocessed_time.is_(None),               # matches error SQL
    )
)
```

### Why Initial Analysis Was Wrong

| Initial Assumption | Actual Finding |
|-------------------|----------------|
| Fallback `file_needs_reprocessing_by_mtime` | `upsert_metadata` concurrent writes |
| Context not being passed | Context IS passed correctly |
| READ path issue | WRITE path issue |

### Error Flow

```
12 parallel workers processing files
    ↓
Each calls upsert_metadata after file copy
    ↓
upsert_metadata runs SELECT query (db.py:558)
    ↓
SQLite on NFS can't handle 12 concurrent sessions
    ↓
Lock timeout → disk I/O error every ~18 min
```

### Key Evidence

1. **Error file exists in output:** `equity_asia1.px.hpc.gz.enc.20260220` was written successfully
2. **Error is soft failure:** File copy succeeds, only DB metadata write fails
3. **Part 1 READ optimization works:** "Bulk read bronze: 0 processed" logged correctly
4. **22,431 output files = 11,215 x 2** (matches log success count)
