#### 2. Code Review: `feature/duckdb-enhancement`

**Branch:** 57 commits ahead of dev, +2900/-84 lines, 14 files

**What it does:** DuckDB-based worker shard merging to eliminate SQLite lock contention during parallel processing. Each worker writes to its own SQLite shard; after each phase (Bronze/Silver/Gold), DuckDB merges all shards into canonical DB via UNION ALL.

**Also includes:** SQLite retention (14 days instead of 1), WAL/SHM sidecar cleanup, NFS compatibility (DELETE journal, no WAL), crash recovery (orphaned shard detection + emergency merge).

**Key new files:**

#### 3. Deep Dive: Silver Not Picking Up Files

**Symptom from prod logs (sp/transcripts_cwiq_pipe):**
```
Cycle 500 complete: Bronze(38/0), Silver(0/0), Gold(0/0) - Total time: 2.28s
```

38 files processed to Bronze successfully, but Silver finds 0 files to process.

**Root cause investigation:**
- Bronze shards merge into canonical after Bronze phase — confirmed working (no merge errors)
- Silver discovery calls `get_bronze_files_needing_silver_processing(db_engine, vendor, dataset, version)` which reads canonical
- This function queries bronze `output_filepath` records and checks which don't have matching silver `input_filepath` records
- If 38 bronze records exist in canonical, Silver should find 38 files

**Possible causes (not yet confirmed):**
1. Bronze `output_filepath` is `None` in the DB records
2. Vendor/dataset/version filter mismatch between Bronze write and Silver query
3. `db_engines` dict empty or pointing to wrong DB at Silver discovery time
4. The bronze records were written but merge didn't actually persist them

**Key log line to check:** `"Found {} total bronze files needing silver processing"` — if 0, the DB query is the problem; if 38, the Silver handler itself is the problem.

#### 4. Architecture Clarification

Discussed and confirmed the shard architecture:
- **Canonical DB**: persistent, accumulates all records, source of truth for all reads
- **Worker shards**: temporary per-phase, created fresh, deleted after merge
- **Each phase**: create shards → workers write → merge into canonical → delete shards → next phase reads canonical

The worker ID race condition (counter cycling can assign same ID to 2 threads) is **low severity** — would cause shard contention warnings in logs, not silent data loss. After merge, data is correct regardless.
